## 1. Единые настройки контейнера для execute_code и terminal

**Статус:** сохранено и доработано в `6adf2cb00c`.

Раньше `execute_code` собирал собственный неполный набор настроек контейнера.
Если он первым создавал среду, часть параметров могла отличаться от среды,
созданной инструментом terminal.

Теперь оба пути используют общий `_container_config_from_config`.
Также исправлена передача списков и словарей из настроек терминала профиля:
вместо `str(value)` используется существующий сериализатор `_terminal_env_value`.
Это важно для структурированных параметров, включая Docker volumes.

Новых настроек нет: используется существующая секция `terminal` профиля.

Код: `tools/code_execution_tool.py`, `tools/terminal_scope.py`.
Проверки: `tests/tools/test_code_execution_config.py` и связанные проверки
конфигурации/терминала. Живой запуск контейнера при ревью не проверен:
Docker daemon в окружении разработки был недоступен.

## 2. Кнопки подтверждения для плагинов в Telegram

**Статус:** сохранено и доработано в `6adf2cb00c`.

Плагин может запросить решение пользователя через `ctx.human_decisions.request`:
заголовок, текст, варианты выбора и срок ожидания. Получатель определяется
по существующей gateway-сессии, а не по произвольному chat id.

- Требуется разрешение плагину `gateway.human_decisions`; по умолчанию выключено.
  Старый ключ `allow_human_decisions` также поддерживается.
- Ответ привязан к исходному пользователю, сессии и конкретному боту.
- Решение одноразовое; просроченные запросы и сменившиеся сессии отклоняются.
- Таймаут включает доставку сообщения. Отмена запроса и выгрузка плагина
  освобождают ожидающие запросы.
- Gateway-команды плагина могут принимать `session_key` именованным аргументом;
  обработчики с прежней сигнатурой продолжают работать.

Это механизм взаимодействия плагина с пользователем. Он не заменяет системные
разрешения инструментов и `ApprovalPolicy`. Поддерживается Telegram.

Код: `hermes_cli/human_decisions.py`, `hermes_cli/plugin_human_decisions.py`,
`gateway/run_human_decisions.py`, `plugins/platforms/telegram/human_decisions.py`
и подключение в загрузчике плагинов/gateway.

Описание API: [Human decisions](website/docs/user-guide/features/plugins.md#human-decisions).
Проверки: тесты human decisions в `tests/hermes_cli/` и `tests/gateway/`,
включая загрузку плагина, маршрутизацию сессии и интеграцию с Telegram SDK
без отправки реальных сообщений.

## 3. Запрет обновления через Telegram для отдельного профиля

**Статус:** реализовано в `69acd9fbf6`.

В `config.yaml` каждого нужного профиля:

```yaml
gateway:
  platforms:
    telegram:
      extra:
        allow_update_command: false
```

Запрещает Telegram-команду `/update`, в том числе администратору.
Проверка происходит до запуска обновлятора. Используется конфигурация адаптера,
который принял сообщение, в том числе при работе нескольких профилей.
По умолчанию значение `true`. CLI-команда `hermes update` этим флагом не запрещается.
После изменения конфигурации перезапусти соответствующий gateway.

Код: `gateway/slash_commands.py`, `hermes_cli/config_defaults.py`.
Проверка: `tests/gateway/test_update_profile_policy.py` — реальные временные
конфиги двух профилей и выбор конфигурации по источнику сообщения.

## 4. Ручной перезапуск gateway после обновления

**Статус:** реализовано в `69acd9fbf6`.

В `config.yaml` профиля, из которого запускается обновление:

```yaml
updates:
  restart_gateways: false
```

Код и зависимости обновляются, но обновлятор не перезапускает сервисы.
Работающие gateway продолжают использовать загруженный код до ручного перезапуска.
По умолчанию значение `true`, допустимы YAML boolean `true`/`false`.

- Настройка действует на этап перезапуска всей установки, включая соседние профили.
- Применяется и к обновлению из CLI, и к обновлению, запущенному gateway.
- Пропускаются отложенные автоматические перезапуски и очистка процессов dashboard.
- Маркер необходимого перезапуска сохраняется. В отчёте обновления записывается
  пропуск, проверка работающих версий откладывается; старый процесс не объявляется
  работающим на новом коде.
- Явная команда `hermes gateway restart` продолжает работать.
- На Windows при работающих gateway обновление с этим флагом останавливается
  до их выключения: процессы блокируют файлы. Остановить их нужно вручную.

Код: `hermes_cli/update_policy.py`, `hermes_cli/update_cmd_fleet.py`,
`hermes_cli/update_cmd_maint.py`, `hermes_cli/update_cmd_windows.py`.
Проверки: `tests/hermes_cli/test_update_restart_policy.py`.

## 5. Одна команда для обновления кастомной ветки

**Статус:** реализовано в `6243b299f6`.

Цель: запустить `hermes update` и получить свежие официальные изменения вместе
с нашими доработками, не теряя локальные коммиты.

На кастомной ветке форка, например `custom`, обычный `hermes update`:

1. Получает `origin/custom` и свежий `main` официального NousResearch/hermes-agent.
2. Объединяет их с текущей веткой через merge. При необходимости создаёт локальные
   merge-коммиты. Повторные запуски сохраняют эту историю.
3. Проверяет синтаксис критических файлов и выполняет обычные этапы обновления
   зависимостей и сборки. Учитывает `updates.restart_gateways`.
4. Ничего автоматически не отправляет в GitHub.

При ошибке получения официального `main` обновление останавливается.
При конфликте объединение отменяется и восстанавливается коммит до обновления,
даже если первый merge уже прошёл. Сообщение перечисляет конфликтующие файлы.
Незакоммиченные правки остаются в указанном stash для ручного восстановления.
Обновление не продолжается до установки зависимостей и не сообщает об успехе.

Для merge-коммита Git нужны настроенные `user.name` и `user.email`.
Ветка должна существовать в `origin`. Автоматическое разрешение содержательных
конфликтов не выполняется: потребуется ручное исправление.

Режим выбирается для кастомных веток форка автоматически. Явный выбор другой
ветки через `--branch`, флаг `--switch-branch`, ветки `main`/`master` и detached HEAD
оставляют прежний путь обновлятора.

Чтобы впервые получить эту доработку на установке с прежним обновлятором,
находясь в ветке `custom`, выполни:

```bash
git pull --ff-only origin custom
```

После этого используй `hermes update`. Если локальная ветка уже разошлась с
`origin/custom`, первая команда откажется от обновления: сначала нужно объединить
истории вручную, сохранив локальные коммиты.

Код: `hermes_cli/update_cmd_custom.py` и подключение в `hermes_cli/update_cmd.py`.
Проверки: `tests/hermes_cli/test_update_custom_merge.py` — настоящие временные
Git-репозитории, повторное обновление обеих удалённых веток, сохранение коммитов
и незакоммиченных правок, конфликты на обоих этапах, ошибка fetch и `merge.ff=only`.
